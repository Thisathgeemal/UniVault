# CLAUDE.md – UniVault

Context for Claude Code. Read this before changing anything in this repository.

## Project

**What it is:** UniVault, a privacy-preserving self-sovereign identity (SSI)
system for Sri Lanka. It's a final year project (BSc Computer Science)
by a solo developer.

**The trust triangle:**

| Role     | Component                                                        |
| -------- | ---------------------------------------------------------------- |
| Issuer   | Employer or bank, using the **issuer portal**                    |
| Holder   | Citizen, using the **mobile wallet**                             |
| Verifier | Organisation checking credentials, using the **verifier portal** |

**Credentials:** SD-JWT Verifiable Credentials. The issuer signs with
**RS256**. Selective disclosure uses SHA-256 digests. The holder's key-binding
proof uses **ES256**. There's no blockchain.

**Use cases:** employee identity verification (Employment credential) and KYC
(KYC credential).

**AI:** an Isolation Forest anomaly detection service checks verification
events (Sprint 4).

**Schedule (agile):** 5 sprints, 16 Nov – 19 Dec 2026, Monday–Saturday, with a
supervisor review every Sunday.

| Sprint | Dates          | Focus                                 |
| ------ | -------------- | ------------------------------------- |
| S1     | 16–21 Nov      | Issuer side                           |
| S2     | 23–28 Nov      | Wallet                                |
| S3     | 30 Nov – 5 Dec | Verifier + selective disclosure (MVP) |

## Coding conventions

- **Strict TypeScript** with `exactOptionalPropertyTypes` and
  `noUncheckedIndexedAccess`. Relative imports end in `.js`.
- **Validation:** validate all input with zod through
  `validate({ body, query, params })`, then read it with `getValidated(res)`.
- **Errors:** throw `AppError(status, CODE, message, details?)`. The central
  handler returns `{ "error": { code, message, details?, requestId } }`. Never
  return stack traces or internal messages in production.
- **Organisation isolation (critical):** the issuer comes from `req.auth`
  (`requireAuth`), **never from the request body**.
  - Another issuer's record must look like `404`, not `403`.
  - Routes with `:issuerId` use `requireOwnIssuer`.
- **Roles:**
  - **Officer:** holders, issue, reissue, offers.
  - **Admin:** everything officers can do, plus revoke, key management and
    the staff list.
- **Privacy (PDPA):** never log claims, names, NIC numbers, passwords, tokens,
  private keys, pre-authorised codes or revocation/reissue notes. Log IDs,
  `action` and `reason` only (`note` paths are in `REDACT_PATHS`).
  - Don't store signed SD-JWTs on the server.
  - Store only hashes of pre-authorised codes.
- **Credential claims:**
  - Validate against `docs/schemas/*.schema.json` through
    `services/credential-schemas.ts`.
  - The selectively disclosable fields, `vct`, `schemaVersion` and
    `defaultValidity` come from each schema's `x-univault` block.
  - `age_over_18` is always calculated by the server (Decision 005).
- **Environment variables:** an empty value means not set. Use `||`, not `??`,
  when reading `process.env` directly. `loadConfig()` already handles this.
- **Database changes:** add a new file `migrations/NNNN_description.sql`.
  **Never edit an applied migration** (it's checksum-protected). Update
  `src/db/schema.ts` to match; `test/db/schema.test.ts` checks the two agree.
- **Reuse `@univault/crypto-core`** for all crypto. Don't re-implement signing,
  hashing or disclosures in the backend.
- **Transactions (PGlite):** inside `db.transaction(async (tx) => …)`, every
  query must use `tx`, never `db`. PGlite has one connection, so a `db` query
  inside a transaction waits forever (Sprint 1, Issue 5).

## Credential lifecycle (important)

| Status       | Meaning                                                                      | Reached by                                           |
| ------------ | ---------------------------------------------------------------------------- | ---------------------------------------------------- |
| `pending`    | Created by staff from a holder record (or a reissue replacement). Not signed | `POST /credentials`, `POST /credentials/:id/reissue` |
| `valid`      | Signed and delivered to the wallet                                           | `signCredential()` at redemption                     |
| `revoked`    | Withdrawn by an admin (final). From `pending` or `valid`                     | `POST /credentials/:id/revoke`                       |
| `superseded` | Replaced by a reissued credential (final). Only from `valid`                 | `POST /credentials/:id/reissue`                      |

**Revoke and reissue (Decision 012, draft).** Revoke is admin-only; reissue is
officer or admin. Both run in one transaction: revoke sets `revoked_at`,
`revoked_by_staff_id`, `revocation_reason`; reissue locks the old credential and
the holder, builds the replacement from the holder's **current** record through
the same code as issuance (`prepareClaims` / `insertPending`: schema validation,
`age_over_18`, expiry caps, optional earlier `validUntil`), supersedes the old one
**immediately**, and inserts the new one as `pending` with
`replaces_credential_id`. Both invalidate the credential's open offers. Reissue
does not create an offer. Every status change (create, sign, revoke, supersede)
is written to the append-only `credential_status_events` table in the same
transaction; `GET /credentials/:id/events` returns it oldest first. Reasons are
fixed enums (also enforced by CHECKs from migration 0006); a `note` (trimmed,
≤ 500) is required for `other` and never logged. `validUntil` (reissue,
optional) means 00:00 UTC on that date.

**Error codes:** `CREDENTIAL_NOT_FOUND` (404, also other issuers),
`ACTIVE_CREDENTIAL_EXISTS`, `ISSUER_KEY_MISSING`, `CREDENTIAL_NOT_PENDING`,
`CREDENTIAL_EXPIRED`, `CREDENTIAL_ALREADY_REVOKED`, `CREDENTIAL_SUPERSEDED`
(`details.replacedBy`), `CREDENTIAL_NOT_REISSUABLE` (all 409);
`VALIDATION_ERROR` (400, invalid request body/path/query only);
`HOLDER_DATA_INVALID` (422, issue **and** reissue: the stored holder record no
longer passes its schema or its ID document expired; `details[]` =
`{ path: "claims.<field>", message }`); `INVALID_HOLDER_KEY` (400); `FORBIDDEN`
(403, e.g. officer revoking).

**Pending means not signed** because the credential must be bound to the
holder's wallet key (`cnf`), which is only known when the wallet redeems the QR
offer (Sprint 2). Signing therefore happens at redemption. Never sign without
a holder key (Decision 010, draft).

**Signing already exists:** `signCredential(credentialId, holderPublicJwk)` in
`backend/src/services/credentials.service.ts` is built and tested. The Sprint 2
redemption endpoint (`POST /credential-offers/credential`) must call it after
finding the offer with `findOfferByCode(code)` in
`services/credential-offers.service.ts` (hash lookup; accept only
`status === 'active'`); don't write a second signing path. It only
accepts an EC P-256 public JWK (no `d`), signs with the issuer's **active** key,
updates `WHERE status = 'pending'` (signed at most once; a revoked or
superseded credential can never be signed), writes the `pending → valid` event
(no staff member) and returns the SD-JWT without storing or logging it.
`findOfferByCode` also returns `credentialStatus` and reports an offer whose
credential is no longer `pending` as `invalidated`.

**Dev-only simulated redemption (TEMPORARY):** until Sprint 2, `POST
/api/v1/dev/credentials/:id/simulate-redemption` (admin, own issuer) calls
`signCredential()` with a throwaway key and returns metadata only. It is mounted
only when `DEV_SIMULATE_REDEMPTION=true` (default false), `createApp()` logs one
warning at start-up when it is, and `loadConfig()` refuses it in production.
**Removal note:** when wallet redemption (`POST /credential-offers/credential`)
ships in Sprint 2, delete `src/routes/dev.routes.ts`, its mount in
`routes/index.ts`, the start-up warning in `app.ts`, `DEV_SIMULATE_REDEMPTION`
(`env.ts`, `.env.example`), `test/dev-routes.test.ts`, and switch
`scripts/evidence/s1-revocation.ps1` to the real redemption flow.

**One active credential per holder and type:** `POST /credentials` rejects a
second `pending` or `valid` credential of the same type (`409
ACTIVE_CREDENTIAL_EXISTS`). The check runs in a transaction that locks the
holder row (`SELECT … FOR UPDATE`), so simultaneous requests can't both pass;
there is no database constraint for it. Reissue supersedes the old credential
before this check, so its replacement passes.

**Unredeemed pending credentials** block a new one for that holder until they
expire, unless an admin revokes them (revoke accepts `pending`).

**Signing keys:**

- **Private keys:** encrypted PEM files in `ISSUER_KEYS_DIR` (git-ignored),
  protected by `ISSUER_KEY_PASSPHRASE`.
- **Public keys:** `issuer_keys` table, published as a JWKS at
  `GET /api/v1/issuers/:issuerId/keys`.

authentication (401), roles (403) and isolation (404 for other issuers). No
secrets or personal data may appear in responses or logs.
