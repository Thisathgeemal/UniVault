# CLAUDE.md – UniVault

Context for Claude Code. Read this before changing anything in this repository.

## Project

**What it is:** UniVault, a privacy-preserving self-sovereign identity (SSI)
system for Sri Lanka. It's a final year project (BSc Computer Science)
by a solo developer.

**The trust triangle:**

| Role     | Component                                                        |
| -------- | ---------------------------------------------------------------- |
| Issuer   | Employer or bank, using the **issuer portal**                    |
| Holder   | Citizen, using the **mobile wallet**                             |
| Verifier | Organisation checking credentials, using the **verifier portal** |

**Credentials:** SD-JWT Verifiable Credentials. The issuer signs with
**RS256**. Selective disclosure uses SHA-256 digests. The holder's key-binding
proof uses **ES256**. There's no blockchain.

**Use cases:** employee identity verification (Employment credential) and KYC
(KYC credential).

**AI:** an Isolation Forest anomaly detection service checks verification
events (Sprint 4).

**Schedule (agile):** 5 sprints, 16 Nov – 19 Dec 2026, Monday–Saturday, with a
supervisor review every Sunday.

| Sprint | Dates          | Focus                                 |
| ------ | -------------- | ------------------------------------- |
| S1     | 16–21 Nov      | Issuer side                           |
| S2     | 23–28 Nov      | Wallet                                |
| S3     | 30 Nov – 5 Dec | Verifier + selective disclosure (MVP) |
| S4     | 7–12 Dec       | AI + Should-haves                     |
| S5     | 14–19 Dec      | Testing and release                   |

## Coding conventions

- **Strict TypeScript** with `exactOptionalPropertyTypes` and
  `noUncheckedIndexedAccess`. Relative imports end in `.js`.
- **Validation:** validate all input with zod through
  `validate({ body, query, params })`, then read it with `getValidated(res)`.
- **Errors:** throw `AppError(status, CODE, message, details?)`. The central
  handler returns `{ "error": { code, message, details?, requestId } }`. Never
  return stack traces or internal messages in production.
- **Organisation isolation (critical):** the issuer comes from `req.auth`
  (`requireAuth`), **never from the request body**.
  - Another issuer's record must look like `404`, not `403`.
  - Routes with `:issuerId` use `requireOwnIssuer`.
- **Roles:**
  - **Officer:** holders, issue, reissue, offers.
  - **Admin:** everything officers can do, plus revoke, key management and
    the staff list.
- **Private keys (Decision 014): only `src/keys/key-store.ts` touches private
  keys.** It alone reads key files, `ISSUER_KEYS_BUNDLE` and
  `ISSUER_KEY_PASSPHRASE`; everything else calls `getSigningKey(issuerId)`,
  `createKeyPair()`, `reload()`, `status()` or `writeBundle()`. Never load,
  decrypt, log, serialise or return a private key anywhere else; routes never
  touch keys (a test in `key-store.test.ts` enforces this). Throw/let through
  `KeyStoreError` (code + issuer id + kid only); the error handler answers
  `503 ISSUER_KEY_UNAVAILABLE`.
- **Frontend (portals, Decisions 015 and 016):**
  - **Staff token: memory + sessionStorage only, NEVER localStorage** (nor any
    other secret). localStorage holds only the language preference
    (`univault.language`). A test spies on `localStorage.setItem`.
  - **Offer codes (Decision 021): the create-offer response (QR text with the one-time
    pre-authorised code) lives ONLY in the offer page's React state.** Never in the URL,
    sessionStorage, localStorage, a TanStack Query/mutation cache (`createOffer()` is called
    directly, not via useQuery/useMutation) or the console. Never fetch or re-show it: opened
    without it while an offer is active, show "can't be shown again" + Generate. Offer status
    queries use `gcTime: 0` and are removed on unmount. The developer panel (decoded
    `credential_offer`) is gated by an INLINE `!import.meta.env.PROD` so the build drops it
    (`scripts/check-production-bundle.mjs`). `issuer-portal/test/offer.test.tsx` spies on
    storage and console.
  - **All UI strings go through `t()`** (react-i18next), including ARIA labels.
    Add every key to BOTH `src/i18n/locales/en.ts` and `si.ts` (typed; a test
    checks key parity, Sinhala script and placeholders). New Sinhala text needs
    native-speaker review.
  - **portal-ui stays app-agnostic:** no routes, API calls or text strings;
    labels and icons are passed in.
  - **Roles:** add a protected page to `src/routes/app-routes.tsx` only; the
    router guard (`RequireRole`) and the sidebar both read it. UI guards are
    convenience: the backend enforces roles.
  - **API calls** go through the `ApiClient` from `useAuth().api` (Bearer
    token, `ApiError`, session-ending 401s → sign-out with returnTo). Server
    data uses TanStack Query; the cache is cleared on sign-out.
  - **returnTo:** only via `safeReturnTo()` (internal paths only).
  - **Times** are shown in Asia/Colombo (`lib/format.ts`).
  - **No inline scripts or styles, no CDN, no CSS-in-JS:** the production CSP
    is `script-src 'self'; style-src 'self'` (csp.ts). `VITE_*` variables are
    public: never put a secret in one.
  - **Lint:** react-hooks 7 (React Compiler rules: no refs read during render),
    jsx-a11y and react-refresh (portal apps only) are on for the portal packages.
- **Wallet (Expo, Decision 022; docs/frontend/mobile-wallet.md):**
  - **Expo Go compatible modules only** until the development build (push notifications or
    OS-level offer links). Add Expo packages with `npx expo install`, pin exactly, keep
    `npm run doctor` at 20/20. Never commit `android/` or `ios/` (generated by prebuild).
  - **crypto-core: universal entry only** (`@univault/crypto-core`); Metro refuses `/node`.
    `index.ts` imports `src/lib/crypto-setup` before anything else (getRandomValues polyfill,
    TextEncoder/TextDecoder/BigInt checks). No `crypto.subtle`, no `Buffer` in app code.
  - **Design tokens:** only from `@univault/portal-ui/tokens`, mapped to the SOURCE file
    `portal-ui/src/tokens.ts` by Metro, tsconfig `paths` and Jest (`app.config.ts` imports it as
    `../portal-ui/src/tokens.ts`), so portal-ui never needs building first; portal-ui is NOT an npm
    dependency of the wallet: a `file:` link fails expo-doctor's duplicate React check). No hex
    colours or copied sizes in `src/` / `app/` (a test and `react-native/no-color-literals`
    enforce it). Change a value in `portal-ui/src/tokens.ts`: the wallet follows at once; rebuild
    portal-ui to regenerate `theme.css` for the portals. Keep tokens.ts import-free and plain
    (Expo's config loader and Node type stripping load it directly). A portal's Tailwind `@source` of portal-ui/src must
    exclude `tokens.ts` and `theme-css.ts` (`@source not`), or words in them become utilities.
    The wallet uses the token sets directly (`theme.colors.brand`, `theme.colors.textMuted`; dark
    values for the same names); theme.css emits the light set only (portals are light-only). The
    portal CSS changes whenever a token does: `portal-ui/test/tokens.test.ts` checks theme.css
    equals what tokens.ts generates (this replaced the old "byte-identical CSS" check).
  - **Routes:** every path comes from `src/navigation/routes.ts` (`ROUTES.*`); never write a path
    string in a screen. A new route file goes into `ROUTE_FILES` (`test/routes.test.tsx` compares

    Each tab folder has a Stack (`TabStack`, `unstable_settings.anchor = 'index'`; not

    `useStackScreenOptions()`. Tabs use `backBehavior: 'firstRoute'` (Android back: stack → first
    tab → leave app only from the Credentials root).
  - **Components:** build screens from `src/components` (catalogue in mobile-wallet.md §5); icons
    only through `Icon` (decorative unless `label`); a credential's status only through

## Credential lifecycle (important)

| Status       | Meaning                                                                      | Reached by                                           |
| ------------ | ---------------------------------------------------------------------------- | ---------------------------------------------------- |
| `pending`    | Created by staff from a holder record (or a reissue replacement). Not signed | `POST /credentials`, `POST /credentials/:id/reissue` |
| `valid`      | Signed and delivered to the wallet                                           | `signCredential()` at redemption                     |
| `revoked`    | Withdrawn by an admin (final). From `pending` or `valid` (incl. expired)     | `POST /credentials/:id/revoke`                       |
| `superseded` | Replaced by a reissued credential (final). Only from `valid` (incl. expired) | `POST /credentials/:id/reissue`                      |

**`expired` is computed, never stored (Decision 013).** `effectiveStatus(record,
now)` in `services/credential-status.ts` is the ONE status rule: revoked >
superseded > expired > valid; expired when `now >= expires_at` (inclusive);
pending stays pending. The public status endpoint and the portal's
`effectiveStatus` field (next to the stored `status` in credential metadata;
`GET /credentials?effectiveStatus=expired`) both use it; in SQL, use its twin
`effectiveStatusCondition(status, now)` (same file; the list filter and the dashboard do). Never write `expired`
to the database. The clock is injected (`createApp(config, logger, { now })`,
`authedTestApp(overrides, logger, { now })`); don't call `Date.now()` in status
logic. Expiry instants are whole seconds, so the SD-JWT `exp` equals
`expires_at`; `jti` = credential id (non-disclosable).

**Public status endpoint:** `GET /api/v1/status/:credentialId`, no login
(`docs/api/status-api.md`). Returns exactly `{ credentialId, status, expiresAt,
checkedAt }`. **Only signed credentials (`issued_at` set) have a public
status:** unknown ids and never-signed credentials (pending, or revoked while
pending) give the same `404 CREDENTIAL_STATUS_NOT_FOUND`. This rule lives in
the status service; `effectiveStatus()` is unchanged, so the issuer API still
shows `revoked` for them. `Cache-Control: no-store`; CORS `*` for GET on
this route only (everything else keeps the `CORS_ORIGINS` allow-list); per-IP
rate limit `STATUS_RATE_LIMIT_MAX` (60) per `STATUS_RATE_LIMIT_WINDOW_MINUTES`
(1) → `429 RATE_LIMITED`. Logs show the route template
`/api/v1/status/:credentialId`, never the URL, on every level (429 warning
included). Lookups are logged at **debug** only (credential id +
result, never an IP) and never stored.

**Issuer dashboard:** `GET /api/v1/dashboard/summary` (officer/admin; issuer ONLY from
the token; `Cache-Control: no-store`; `docs/api/dashboard-api.md`). One aggregate query
(`COUNT(*) FILTER`) with the injected clock: `issued` = signed (`issued_at IS NOT NULL`);
`active` = issued + effective `valid`; `revoked` / `superseded` = issued + that status;
`expired` = issued + effective `expired`; `awaitingWallet` = `pending`; `expiringSoon` =
active + `expires_at < now + 30 days`; `holders` = the issuer's holders. Revoked-while-pending
is in no issued count. Invariant: `issued = active + revoked + superseded + expired`. Plus the
last 10 status events (reason codes and staff names only; never notes or claims). The list's
`effectiveStatus=revoked` total also includes revoked-while-pending (dashboard does not).

**Dashboard demo data (DEV ONLY, Decision 017):** `npm run db:seed:demo` (needs `db:seed`,
`keys:init`; refuses production) creates, for Serendib Trading (`employer-a`) only, credentials
of every status through the real services (sign, reissue, revoke, `simulateExpiry`, offers;
past steps with an injected clock). Every action is done by an inactive account
`demo-data@serendib-trading.example`, which marks the demo rows: re-running skips, `--reset`
removes only them plus credentials chained to them via `replaces_credential_id` (staff
reissues of demo credentials, transitively) with their offers and events (it lifts the append-only trigger on `credential_status_events` inside its
one transaction). Prints counts per status only. The e2e backend runs it too.

**Revoke and reissue (Decision 012, draft).** Revoke is admin-only; reissue is
officer or admin. Both run in one transaction: revoke sets `revoked_at`,
`revoked_by_staff_id`, `revocation_reason`; reissue locks the old credential and
the holder, builds the replacement from the holder's **current** record through
the same code as issuance (`prepareClaims` / `insertPending`: schema validation,
`age_over_18`, expiry caps, optional earlier `validUntil`), supersedes the old one
**immediately**, and inserts the new one as `pending` with
`replaces_credential_id`. Both invalidate the credential's open offers. Reissue
does not create an offer. Every status change (create, sign, revoke, supersede)
is written to the append-only `credential_status_events` table in the same
transaction; `GET /credentials/:id/events` returns it oldest first. Reasons are
fixed enums (also enforced by CHECKs from migration 0006); a `note` (trimmed,
≤ 500) is required for `other` and never logged. `validUntil` (reissue,
optional) means 00:00 UTC on that date.

**Reissue preview and expired credentials (Decision 012 consequences).** `reissue()` and `POST
/credentials/:id/reissue/preview` share `prepareReissue()` (like `prepareIssuance()`; the preview
passes `{ lock: false }`, writes nothing, `no-store`, returns `current` / `replacement` claims and
expiry, `cappedBy`, `changedFields` via `changedClaimNames()`). Its one-active-credential check
runs BEFORE the supersede and excludes the credential being replaced. Checks use the STORED
status, so an **expired** credential (stored `valid`) **can be renewed by reissue** (any reason,
usually `validity_extension`; the portal calls it "Renew") and **revoked** by an admin. In the
portal, `credentialActions()` (`issuer-portal/src/credentials/actions.ts`) is the one action rule:
valid → Revoke (admin; officer sees it disabled "Only administrators can revoke credentials"),
Reissue; pending → Revoke (admin), Create / Show wallet offer; expired → Renew, Revoke (admin);
revoked / superseded → view only. After any action `invalidateAfterCredentialChange()` refreshes
`['credentials']`, `['dashboard','summary']` and `['holders']`.

`ACTIVE_CREDENTIAL_EXISTS`, `ISSUER_KEY_MISSING`, `CREDENTIAL_NOT_PENDING`,

holder's wallet key (`cnf`), which is only known when the wallet redeems the QR
offer (Sprint 2). Signing therefore happens at redemption. Never sign without
a holder key (Decision 010, draft).

**Issuance preview (Decision 019): claims are never assembled or edited in the portal;

issuance, `{ lock: false }` for the preview →
`prepareClaims()` → one active credential → active key); the preview writes nothing

signer's builder; `iat` planned, `jti`/`cnf`/`status` null), `disclosable`, `derived`, `expiry
{ expiresAt, defaultExpiresAt, cappedBy, validUntilRange }`. `POST /credentials` accepts
`validUntil`. `GET /credential-schemas` returns the ONE schema of the issuer type, its fields
flagged from the schema file (`required`, `selectivelyDisclosable`, `derived`) and the
always-visible claim names; never keep a field list in code. Another type → 400.

**Signing already exists:** `signCredential(credentialId, holderPublicJwk)` in

`findOfferByCode` also returns `credentialStatus` and reports an offer whose

**One active credential per holder and type:** `POST /credentials` rejects a
second `pending` or `valid` credential of the same type (`409
ACTIVE_CREDENTIAL_EXISTS`). The check runs in a transaction that locks the
holder row (`SELECT … FOR UPDATE`), so simultaneous requests can't both pass;
there is no database constraint for it. Reissue's check leaves out the credential
being replaced, so its replacement passes.

**Unredeemed pending credentials** block a new one for that holder until they
expire, unless an admin revokes them (revoke accepts `pending`).

**Signing keys (`docs/security/issuer-key-management.md`, Decision 014):**

- **Private keys:** encrypted PKCS#8 only (unencrypted keys are refused), from
  `ISSUER_KEY_SOURCE=file` (`<kid>.private.pem` in `ISSUER_KEYS_DIR`,
  git-ignored) or `env` (`ISSUER_KEYS_BUNDLE` = base64 JSON `[{ issuerId, kid,
encryptedPrivateKeyPem }]` from `npm run keys:bundle`), always decrypted with
  `ISSUER_KEY_PASSPHRASE`. Decrypted once and cached as a `KeyObject`;
  rotation clears and reloads. Env mode cannot rotate through the API (409).
- **Retry backoff:** a failed load (any `KeyStoreError`) is remembered for
  `KEY_RETRY_BACKOFF_SECONDS` (default 30, 0 = off); within it `getSigningKey`
  rethrows the cached error without decrypting, after it the next call retries.
  `reload()` / rotation clears it at once. Tests inject the clock
  (`createKeyStore({ …, now, retryBackoffSeconds })`).
- **KeyStoreError codes:** `KEY_NOT_FOUND`, `KEY_DECRYPT_FAILED`,
  `KEY_UNENCRYPTED`, `KEY_KID_MISMATCH`, `KEY_PUBLIC_MISMATCH`,
  `KEY_SOURCE_INVALID`.
- **Start-up check** (`server.ts`, after migrations, before listening): every
  active key is decrypted, its RFC 7638 thumbprint must equal the stored kid
  and its public key the stored JWK. Strict (exit 1) always in production or
  with `ISSUER_KEYS_STRICT_STARTUP=true`; otherwise it warns and starts

## Testing

**Wallet tests (Jest, not Vitest):** `wallet/test/setup.ts` **fails a test on any unexpected
`console.error` or `console.warn`** (listed after the test; `CONSOLE_ALLOW_LIST` is for
documented, unavoidable third-party noise only and is empty). Fix the cause, never silence it:

- **`renderRouter` route maps must match `app/`.** A partial map under a layout that declares
  screens gives expo-router "Too many screens defined" / "No route named …". To test the root
  layout, render the REAL tree: `renderRouter(join(__dirname, '..', 'app'), { initialUrl })`.
- **One render per test,** and await every update (`await user.press(...)`, `findBy*`,
  `waitFor`); two renders or un-awaited updates in one test give React's "overlapping act()
  calls".
- A test that expects an error (ErrorBoundary) mocks `console.error` itself. `clearMocks` is on
  (fresh call counts per test).
- `test/setup.ts` installs the official AsyncStorage mock and an in-memory `expo-secure-store`
  mock (`mockStore`; `expo-crypto` random bytes from Node's CSPRNG), both cleared before each
  test and then seeded with a holder who finished onboarding and has a PIN verifier for
  `TEST_PIN` (`test/setup-state.ts`,
  so the gate opens the tabs; gate / onboarding tests start with `freshInstall()` or
  `seedOnboardedWithoutSecurity()`) and mocks the Sinhala font and splash screen for the root
  layout. The mock's `setItem` goes through `multiSet` (a write shows in both call lists). **Never `jest.spyOn` + restore the
  AsyncStorage mock's functions:** they are `jest.fn`s and restoring removes their in-memory
  store (later tests then pass against a dead store). Use `(AsyncStorage.getItem as
jest.Mock).mockRejectedValueOnce(…)` / `mockImplementationOnce`.
- RNTL leaves elements hidden from screen readers out of queries: a decorative element is found
  only with `{ includeHiddenElements: true }` (that absence is itself the accessibility check).
- With several tab stacks mounted, query the stack header's back button by `stack-header-back`.
- With parallel workers and piped output Jest hides per-file console output, so the guard (not
  the log) is what keeps the suite silent; `npx jest --runInBand` shows the messages.
- Run Jest **and Metro / `expo export`** from PowerShell or cmd: under Git Bash, Metro cannot
  resolve the linked `@univault/crypto-core` (the same drive-path issue as Vitest).

**Framework (all other packages):** Vitest. HTTP tests use supertest. Database tests use
`freshDatabase()`, an in-memory PGlite (`test/db/helpers.ts`).

**Authenticated tests:** `authedTestApp(overrides?, logger?)` in
`test/auth-helpers.ts` gives a seeded database with 3 issuers and 6 staff,
plus `login()` and `tokenFor()`.

- **Staff:** `STAFF.employerAdmin`, `employerOfficer`, `bankAdmin`,
  `bankOfficer`.

**Fixtures:** `test/fixtures/seed-data/` (3 employees, 2 customers). Their

**Two Vitest projects (`vitest.config.ts`, Sprint 1 Issue 15):** `npm test` and
`npm run test:coverage` run both and report one combined result and one
coverage report.

- **fast:** everything in process (supertest, in-memory PGlite). Files run in
  parallel. `npm run test:fast` runs only this project (about a minute less
  waiting while iterating).
- **heavy:** files listed in `HEAVY_TESTS`: `server.test.ts`,
  `key-startup.test.ts`, `check-secrets.test.ts` and `db/seed-disk.test.ts`.
  They spawn real processes (server, CLI, git) or open PGlite **on disk**.
  They run **after** the fast project (`sequence.groupOrder`) with file
  parallelism off. `npm run test:heavy` runs only them.
- **Why:** in parallel with the other files, these tests took 3–10× longer on
  Windows (on-disk PGlite 2.8 s alone → 17 s; a server start 4 s → 35 s) and
  timed out on a slower machine.
- **Rules for a new test** that spawns a process or uses `pglite://<folder>`:
  - add the file to `HEAVY_TESTS`;
  - track every child and kill it in `afterEach` (wait for its exit, capped at
    10 s);
  - give `spawnSync` / `execFileSync` a `timeout`;
  - close on-disk databases in `afterEach`;
  - give each test an explicit, named timeout.
    Don't raise the global `testTimeout` (30 s) or `hookTimeout` (60 s).

**Time in tests (Sprint 1 Issue 20):** never mix an injected clock with real time in one
test; never compare fixed dates to the real clock. Data created at a fixed `NOW` must be
checked at that clock (or a fixed offset from it). Pass the same `now` to every call, or
freeze time with `vi.useFakeTimers({ toFake: ['Date'] })` / `vi.setSystemTime()` and
restore it afterwards. Tests that use real time stay relative to it (`Date.now() ± n`). No
test may depend on today's date.

**Timeouts:** each test file starts PGlite, which is slow on Windows. Keep the
generous timeouts in `vitest.config.ts`.

**Coverage thresholds (backend):** `vitest.config.ts` fails `npm run
test:coverage` below statements 90%, branches 86%, functions 93%, lines 90%
(set 25 Nov 2026, just below the measured figures). Raise them when coverage
improves; never lower them to make a change pass.

**Coverage of each feature:** test the positive path, the invalid input,
authentication (401), roles (403) and isolation (404 for other issuers). No
secrets or personal data may appear in responses or logs.
